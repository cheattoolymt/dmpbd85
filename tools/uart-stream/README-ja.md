# Uno R3：20秒間の立ち下がり時刻の連続転送

最初の192エッジで終了する旧スケッチに代わり、20秒間監視しながら、
リングバッファからPCへ記録を転送する。UART文字そのものや電圧波形の記録ではなく、
D8入力の立ち下がり時刻を0.5µs単位で保存する。

## 配線と書き込み

電源を外して配線する。BD85のF→Uno D8、確認済みの基板GND→Uno GND。
旧ループバック用D0–D8 / D0–D1 / RESET–GNDは外す。
BD85とUnoの電源端子同士はつながない。

Arduino IDEで `bd85_uart_stream/bd85_uart_stream.ino` を開き、Arduino Unoに書き込む。
Arduino IDEのシリアルモニターは閉じる。

## Tera Termでの記録

1. UnoのCOMポートを開く。
2. **1000000 baud / 8bit / パリティなし / ストップ1 / フロー制御なし** に設定する。
   1000000はPC–Uno間の速度であり、BD85側の設定変更ではない。
3. `BD85 stream` の案内が読めることを確認する。
4. 「ファイル→ログ」で `bd85_stream.bin` を指定し、**バイナリをON**。
   「画面バッファを含める」はOFF。ローカルエコーもOFF。
5. `g` を送る。`ARMED` が出たらBD85を起動する。
6. 記録中はバイナリデータなので画面が文字化けする。これは正常。
7. 約20秒後の `DONE,observed=...,buffer_dropped=...,sent=...` を待ってログを終了する。
8. コピーした画面文字ではなく、元の `.bin` を解析する。

1000000で案内自体が読めない場合は、測定を続けずPC–Uno間の通信条件を確認する。
Uno R3の16MHz UARTで1000000 baudは整数分周で生成できる。
実際のPC・ドライバー・USB変換側も含めた動作は実機で確認する。

## 解析

Python標準ライブラリーだけで復元できる。

```sh
python3 tools/uart-stream/decode_stream.py bd85_stream.bin --csv edges.csv
```

既存のCSVは上書きしない。各フレームのCRC・通し番号・最終件数を検証し、
欠けたログや破損したログを黙って正常と扱わない。
`buffer_dropped` はUnoのリングバッファが満杯で保存できなかったエッジ数。
0以外なら全件を保持できていない。

**0でもハードウェアでの取りこぼしがないとは保証できない。**
ATmega328Pの入力キャプチャレジスターにはエッジの待ち行列がなく、
割り込み処理が追いつかないほど速い信号は上書きされ得る。
この種類の欠落は本スケッチのカウンターでは検出できない。
立ち上がり時刻・パルス幅・UARTのフレーミングも記録していない。

## 転送形式

冒頭の案内に続く8バイト `BD85STR1` が記録の開始。
その後は `a5 5a`、type(u8)、payload長(u8)、通し番号(u16 LE)、payload、
CRC16(u16 LE)の順。CRCはtypeからpayload末尾までのCRC-CCITT、
多項式0x1021、初期値0xffff、反転なし・最終XORなし。
payload上限64バイト、通し番号はu16で循環する。

- type 1：前の保存エッジからの経過tickをunsigned LEB128で連結。
  最初の値は記録開始からの経過tick。1 tick＝0.5µs。値はフレームをまたいでよい。
- type 2：u32 LE×4で記録予定時間ms、観測数、リング欠落数、保存・転送数。

最終フレームの後に人間向けDONEメッセージが続く。

## 検証とライセンス

Arduino AVR Core 1.8.6、avr-gcc 7.3.0、ATmega328P/16MHz向けにビルド成功。
フラッシュ4,312バイト、静的RAM1,310バイト。
復元処理はフレームをまたぐ可変長値、時刻復元、欠落数を確認し、
CRC破損・途中終了・不正フレームを拒否することを確認した。
実機での連続転送・最大処理速度の検証は未実施。独自コードはMITライセンス。
